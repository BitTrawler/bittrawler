# 0005 — Confirming classifications against TMDB

Status: accepted.

## Decision

A confirmation stage sits between classification and persistence. It asks TMDB
about every classification that could be wrong, and it may correct that
classification or attach a content reference. It never invents one: a miss
proves nothing, because most adult releases are absent from TMDB and so are
many obscure legal releases.

    metadata → classify → confirm against TMDB → persist

- The stage is a bounded queue with its own workers, so an API call never blocks
  a metadata fetch. The row is still built once, after classification, and
  written once.
- An error, a timeout or no match passes the row through unchanged.
- Candidates are films, shows, and adult classifications that rest only on weak
  markers. A strong adult classification is never looked up.
- Matching uses the scene title parser and requires the normalised title to
  match exactly and the year to be within one. When a film and a show share the
  title, the more popular one has to be clearly ahead (2×) or the lookup is
  treated as ambiguous.
- Corrections are asymmetric:
  - An adult flag is believed outright and turns the row into XXX.
  - A non-adult film match on a weak adult classification turns it back into a
    film. This is the "Sex Drive" case.
  - A show found for a film is believed, and a film found for a show is believed
    only when the name carried no episode information.
  - A show match on a weak adult classification proves nothing about adult
    content and is ignored.
- A confident match stores its TMDB id in `content_id`; the stored category says
  whether the id is a film or a show. Adult matches store no id.
- The cache is in memory only, bounded (50,000 lookups), with a one-day TTL for
  misses and seven days for matches. Restarts re-query; the request budget is
  small enough that this does not matter.
- Requests are rate limited (4/s by default), retried once on 429 and 5xx, and
  the stage stops calling after repeated failures. Without a token the stage is
  not constructed at all.
- The token is configuration, never source. The working copy reads it from a
  file outside the repository.

## Why

The site list and kink list in the classifier are broad, and broad word lists
produce false positives on mainstream films: a legal release group called
HANDJOB, the film "Dick", "Kick-Ass". On the 5,459 classified sample torrents
that bitmagnet also classified, 96.6 % of the rows the classifier calls adult
are adult to bitmagnet as well; the disagreements are chiefly adult releases
that bitmagnet types as films (Fansly, Mofos, ManyVids) and a handful of
mainstream titles whose names contain an adult word, which TMDB resolves:
"Kick-Ass 2" and "Dick" come back as films. In the other direction, 168 rows
that bitmagnet types as adult are classified as films from the name alone;
those are adult releases whose names carry none of the markers, and TMDB can
only help where it knows the title.

Live run (two minutes, first crawl with the stage enabled): 22 lookups, 9
matches, 2 corrections, 1 adult flag, 0 failures. The corrections were an anime
anthology that is a show, and an adult release that the classifier had called a
film. Distinct titles dominate a short run; the cache mainly serves repeated
releases of the same title over a day.

## Limits

- A title that TMDB does not know stays with the classifier's verdict.
- The title parser is a heuristic. Names without a scene structure, mixed
  language titles and CJK titles often produce no usable title and are skipped.
- `search/tv` has no adult flag, which is why a show match cannot confirm or
  deny adult content.
- TMDB is a third-party dependency with its own terms and rate limits. The
  stage is optional and the product works without it, with lower precision.
